一、总体架构

项目是单进程本地 Web 应用。cassie_play.py 包含全部 Bottle 路由（网页 + /api/v1）、CASSIETerminal 业务对象和 pygame/pydub 音频处理；前端已拆分为 cassie_play.html、static/app.js 与 static/advanced.css；Python 客户端在 cassie_api.py，支持进程内与远程两种模式。Cheroot 提供多线程 HTTP 服务。

语法解析
parse_broadcast_text() 将文本与嵌套指令解析成队列和错误。
统一解释
interpret_broadcast_text() 应用音高、语速、音效、铃声和时间线，返回已处理音频事件列表。
播放与导出
play_broadcast_stream() 和 export_from_queue() 消费同一事件计划，分别交给 pygame 和 pydub 输出。
资源层
cassie/words 和 cassie/sounds 通过文件名提供音频素材。

二、模块与关键职责

位置/符号职责扩展点
CASSIETerminal保存运行配置、加载预设、管理音频和播放锁。新增配置时同步初始化、前端保存接口和导出参数。
parse_segment()处理单段文本、单词映射、指令前缀、标点和数字。增加指令时返回新的队列项，避免在解析层调用 pygame。
process_number()把数字转换成英语音频词列表。扩展数字范围或负数规则，并为缺失音频提供错误信息。
apply_broadcast_effect()逐词效果链：滤波、增益、压缩、尾音和噪声（不含混响）。添加 pydub 可表达的效果，注意实时播放与导出共用状态。
play_audio_on_channel()加载或处理单个 WAV 后提交到 pygame 声道。保持返回处理后时长，调用方依靠它计算声道时间线。
_generate_fdn_tail()反馈延迟网络：8 条互质延迟线 + Hadamard 反馈矩阵 + 反馈回路内一阶低通，按块处理。增加导出格式或新队列项时同时更新时间线逻辑。
Bottle 路由提供页面、拼写检查、预设、播放、导出和高级设置 API。新 API 应避免直接暴露可变全局状态。

三、数据流与并发

浏览器 POST /play -> play() 获取 play_lock，写入请求选项 -> interpret_broadcast_text() -> 时间、声道、音高、效果均已落实的 AudioSegment 事件列表 -> play_broadcast_stream() 按时间提交到 pygame -> 等待声道结束，stop_all_audio()，释放锁 浏览器 POST /export -> export_wav() 获取同一把 play_lock -> interpret_broadcast_text() 生成同一事件列表 -> _export_from_queue_unlocked() 叠加事件并写出 WAV

[gap:n] 会推进当前声道时间线。[channl:+0.125] ... [channl:stop] 会把区块解析为独立的嵌套队列，分配空闲声道，并相对区块所在位置偏移；正数延后，负数提前，最多三位小数。区块内的其他指令仍由同一解析器处理。

播放和导出共享 play_lock 与事件解释结果，因此高级效果和时间线只在 interpret_broadcast_text() 中实现一次。铃声使用第 8 号声道，正文使用 0 到 7 号声道。

四、音频实现

变速与音高

音高通过调整 frame rate 后重新采样实现；负语速按静音检测结果裁剪头尾，正语速转成单词之间的等待时间。它不是传统时间拉伸，因此极端倍率会改变听感。

数字短语

数字解析返回 ('number', words)，播放和导出会先拼接组成完整短语，再进行一次处理，避免短音频逐个编码导致音质不一致。

走廊混响

apply_room_reverb() 直接把音频当作反馈延迟网络的输入（_run_fdn() 负责分块推进环形缓冲区）。每条延迟线的反馈增益由 RT60 决定：g = 10 ** (-3 * delay_seconds / RT60)。频率相关的吸收（高频衰减更快）用「一阶低通 + 干湿混合」做在反馈回路内：直流增益恒为 1，因此低频 RT60 严格等于设定值；4 kHz 的增益由 damping_ratio() 反解，可调到低频的 0.4~1.0 倍。这里有两个坑：纯一阶低通会把低中频一起压掉，整条拖尾几十毫秒就衰完；cumsum 实现里要乘 pole^(-k)，极点超过 0.8 或分段过长都会超出 float64 有效位数，同样会把低频拖尾压短——因此极点固定 0.8、按 64 采样分段。网络参数按 采样率 + 声道 + 混响参数 缓存；混音前把湿声起始窗的 RMS 对齐到干声，因此“混响湿声”是一个可预期的混音比例。参数变化时缓存自动落空。混响作用在整段广播上而不是逐个单词：逐词处理会把每个单词的时间槽撑到 RT60 那么长，整条时间线被拉长几十秒；现在由 apply_reverb_to_events() 在时间线组装完成后统一施加，每个事件只保留一份已处理音频，播放与导出必然一致。

高级效果

效果链由 apply_broadcast_effect() 控制。高音延长使用高通后的 FFT 主频生成指数衰减正弦尾音；噪声由 colorednoise 生成后叠加。新增效果应关注音频声道数、采样率和输出长度。

文件句柄

pydub 的 AudioSegment.from_wav(path) 与 export() 都会把打开的文件对象留在对象里，等垃圾回收才关闭：控制台会一直刷 ResourceWarning: unclosed file，长时间运行还会耗尽文件描述符，播放路径更会在临时目录累积 WAV。因此读取统一走 load_audio()、写出统一走 export_audio()，两者都显式关闭句柄；播放时分两步，先把导出的数据读进内存再删除临时文件，pygame.mixer.Sound 用 io.BytesIO 构造。改动这段代码时，可配合 python -W error::ResourceWarning 跑一次播放与导出，确认控制台不再出现该警告。

空音频事件

开启空间效果后，时间线上会多出一个「收尾哨兵」事件（silent: True），它只有 start_ms/end_ms、没有音频，用来把总时长延长到最后一个拖尾结束。这类事件绝不能交给 pygame：AudioSegment.empty() 的 frame_rate 是 1，导出的 WAV 极短，SDL_mixer 在已经持有其它长音频时会越界访问，整个进程以 0xC0000005 退出，Python 层捕获不到。因此播放循环会先过滤掉空音频事件，_play_audio_segment() 自身也再挡一道；导出时则跳过它取采样参数，只用它的时间戳决定输出长度。改动后务必开启空间效果实际播放一次，确认进程不会异常退出。

空间效果的两级开销控制

FDN 的开销 ≈ 处理样本数 ÷ 块长。两个维度可调：块长（只影响主循环迭代次数，不改变声音）与拖尾长度（决定每个词要多算多久，会改变听感）。SPATIAL_QUALITY_LEVELS 把两者打包成七档，第 0 档等于历史行为（block=64、拖尾系数 0.35）。块长始终受两条约束：不超过最短延迟线（否则环形缓冲区读写互相覆盖）、不超过阻尼分段的精度上限。第 6 档在极限档基础上再开 mono_reverb：把立体声混响合成单声道，干声仍是立体声，只是拖尾失去宽度，换来近一倍的额外加速。再往下已经没有空间——单词本体本身就是必须处理的样本，约 12ms/声道是算法硬下限，所以没有第 7 档。

spatial_mode 决定后处理的组织方式。word 对每个事件单独加混响，每个词都跑满一条拖尾，耗时随词数线性增长；sentence 先按声道把时间线拼成干声，再整体跑一次效果链与混响，拖尾只算一次。整句模式下逐词效果链也一并推迟到整轨上执行，否则同一段音频会先逐词加一遍尾音与底噪、再整体加一遍。关键约束：正文边界必须在替换事件之前记录——整句那条事件自带拖尾，它的 end_ms 等于整轨长度，事后从事件上反推会把拖尾算进正文。因此解释器通过线程局部的 _PENDING_TIMELINE 把 content_ms / duration_ms 带回来，两种模式对外给出的时间线完全一致。

为什么 app.js 需要启动自检

app.js 是一整段脚本，顶部任何一处 ReferenceError 都会让后面所有绑定失效，表现成「页面能显示、点什么都没反应」——而且控制台只有一条错误，很容易被忽略。实际发生过两次：on(exportBtn, ...) 里 exportBtn 从未声明，导致 on(playBtn, 'click', playBroadcast) 永远绑不上；以及「减少耗时」滑块没被加进 advancedSliders，所以拖动了右侧文案也不更新。两者都不是后端问题。由于 app.js 是单段脚本，改动后请打开浏览器控制台确认没有红色报错，并实际点一遍播放、导出、中英切换与高级设置的保存——这是唯一能拦住这类问题的手段。

进度条为什么不能只靠事件驱动

播放与导出的进度条读的是服务端真实进度。四个阶段在总进度里的区间由 PROGRESS_SPANS 定义：parse 0~8%、reverb 8~72%、export 72~80%、play 80~100%。百分比必须跨阶段单调递增：每一阶段各自从 0 算起的话，关掉空间效果时 reverb 阶段被跳过，百分比会一直停在 0%，进度条看起来完全不动。因此 progress_percent() 里对上一帧的百分比取了最大值。

更麻烦的是事件密度。关掉空间效果时整条合成只要约 47ms，服务端会在同一瞬间推完所有事件；如果前端按「收到事件才改宽度」来做，浏览器只会渲染出最终结果，用户看到的就是「进度条有、但不动」。所以宽度改成按时间补间：事件只负责设定目标值，由 requestAnimationFrame 在 EXPORT_PROGRESS_FILL_MS（450ms）内追上去。这一点最容易在改动补间逻辑时被破坏：如果改成"收到事件才改宽度"，关掉空间效果时进度条就会完全不动。

预处理阶段（8~72%）的百分比是估算的。逐词加空间效果在 interpret_broadcast_text() 内部同步跑完，那期间生成器根本没法 yield，事件只能在它结束后一次性到达——实测 16 条 reverb 事件全部挤在同一毫秒。所以后端先发一条带 estimated: true 的预估事件（estimate_preprocess_event() 按词数与档次估算），前端据此在 reverb 区间内先自行推进，真实事件到达后覆盖它。最终值准确，只是过程是估的。

播放阶段相反：后端只在起点发一条带 is_playback、duration_ms、started_at 的事件，其余由前端按真实播放时间推进，所以播放期间进度条是连续走的。进度条本身常驻，空闲时写「就绪」，不隐藏——只在导出时显示的话，47ms 的合成根本来不及被看到。

高级设置的持久化

高级设置以前只存在内存里，关掉程序就回到默认值，用户会以为「保存没生效」。现在写入 settings.json：save_settings() 把 API_MUTABLE_FIELDS 里的字段落盘，apply_stored_settings() 在 __init__ 末尾套用（旧版本留下的陌生字段忽略，非法值纠正），网页端与 API 写入默认值时都会保存。按次覆盖（请求体里带参数）不落盘——那只是临时生效，写进去会污染用户的默认设置。

静态资源必须禁用启发式缓存

Bottle 的 static_file() 只发 Last-Modified、不发 Cache-Control。这种响应浏览器会按「启发式缓存」自行决定缓存多久（可达数小时），后果是改了前端但用户还看到旧页面——连 cassie_play.html 本身都被缓存，于是脚本标签上的 ?v= 版本号根本到不了浏览器，用户怎么刷新都没用。排障时因此反复误判成后端问题。

现在所有页面与静态资源都走 serve_local_file()，显式发 Cache-Control: no-cache, must-revalidate。注意不能直接用 static_file() 再加 header：它把自己那批 header 延后到响应收尾阶段才写入，路由里 set_header 会被它覆盖，所以这里改成自己读文件、自己设 Content-Type 与 Content-Length，并做目录穿越校验（规范化后必须仍在 root 内）。

播放日志必须逐词念出"实际听到的内容"

日志行是 [n/m] 内容。内容一律由 spoken_label() 生成，规则是：

  • 数字音频的文件名就是数字（11.wav 读作 eleven），必须经 NUMBER_WORDS 还原成读法，否则用户听到 eleven、日志却写 11；
  • the_vowel / the_consonant 听起来都是 the；
  • 字母音文件是 _a ~ _z，去掉下划线。

整句模式的时间线上每个声道只有一条音频，但那条事件额外用 words 字段保留该声道念过的全部词，播放循环据此逐条输出——所以两种模式的日志完全一致，不会出现 整句 这种用户从没听到过的字样，[n/m] 里的 m 也等于实际行数。

多段数字要逐段成行。数字是一串音频拼起来的（123 读作 1 hundred and 20 3，共 5 段），日志也必须给 5 行：

[1/5] one
[2/5] hundred
[3/5] and
[4/5] twenty
[5/5] three

因此事件上除了 label（拼好的单行文本）还保留 spoken_words（成分片段列表），播放循环优先按片段逐条输出。整句模式的事件也用 spoken_words 汇总该声道的全部片段，所以两种模式的日志逐行一致。

六、自定义指南

增加单词

把小写 WAV 放入 cassie/words/，文件名即输入词。运行 python tools/test_2.py 更新列表；运行时 load_word_set() 也会扫描目录。

增加铃声

把 WAV 放入 cassie/sounds/。普通背景铃声使用 bg_数字.wav 命名；自定义特殊铃声可通过高级设置的文件名选择。

增加指令

在 parse_broadcast_text() 中解析新语法并生成队列项，在 interpret_broadcast_text() 中将它解释成时间、声道和处理后的音频事件。播放和导出只消费事件列表，不要再分别实现指令或效果逻辑。

增加前端设置

添加 HTML 控件、读取和保存字段、后端 GET/POST 字段，并在解释器生成事件计划前更新对应配置。共享配置应逐步改为请求快照，以降低多线程请求互相覆盖的风险。

验证建议

  • 运行 python -m py_compile cassie_play.py。
  • 运行 python diagnostic.py 检查环境和素材。
  • 用 SDL_AUDIODRIVER=dummy 做无硬件播放流程测试。
  • 分别验证纯单词、数字、指令、铃声、多声道、导出和异常清理。
